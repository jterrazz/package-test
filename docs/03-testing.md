# 03 — Testing

What proves a change here: this package specifies itself with itself. The suites under `specs/` are written with `@jterrazz/test` against fixture apps, the module tests sit beside the modules they cover, and a family of meta-tests runs the framework on its own output. This chapter says which suite answers for what, and what a change owes each of them.

The suffix says the kind, as in any consumer ([05 § Which kind of test](05-getting-started.md#which-kind-of-test)); `file-suffix-matches-place` holds it, and its `--fix` renames with `git mv`.

| Ground          | Where                                                         | Proves                                                                                  |
| --------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Module tests    | `src/**/<file>.test.ts`                                       | One module's behaviour, beside it (rule `test-beside-its-module`)                       |
| Component tests | `specs/component/<capability>/<file>.test.tsx`                | A rendered unit, beside it, in a real Chromium ([09](09-component.md))                  |
| Product specs   | `specs/<facet>/<subject>/<aspect>.spec.ts`                    | The framework's own facets, through the public surface                                  |
| Spec documents  | `specs/cli/<domain>/<case>.spec.yaml`                         | A cli session as data, collected as a test file by `literate()` ([15](15-documents.md)) |
| Meta-tests      | `lint/self/corpus/*.test.ts`, `lint/self/catalogue/*.test.ts` | The framework applied to itself and to its own projections                              |

## The nine projects

`test.projects` in `vitest.config.ts` declares nine, and which one you can run is decided by what is installed and running on the machine.

| Project       | Collects                                                                                                               | Needs                                                                  |
| ------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `unit`        | `src/**/*.test.ts` and `lint/**/*.test.ts`, built by `unit()`                                                          | Nothing                                                                |
| `lint`        | `specs/lint/**`, built by `lint()`                                                                                     | `npm run build` first — the plugins and the checkers load from `dist/` |
| `cli`         | `specs/cli/**`, built by `cli()`, plus the documents `specs/cli/run/*.spec.yaml` (depth 1 only) through `literate()`   | Nothing — the Docker specs self-skip                                   |
| `api`         | `specs/api/**`, built by `api()` (node mode, in-process Hono)                                                          | Docker                                                                 |
| `job`         | `specs/job/**`, built by `job()`                                                                                       | Docker                                                                 |
| `integration` | `specs/integration/**`, built by `integration({ serial: true })` — the container seams included                        | Docker                                                                 |
| `website`     | `specs/website/**`, built by `website()`                                                                               | playwright + `npx playwright install chromium`; no Docker              |
| `component`   | `specs/component/**/*.test.tsx` and `src/**/*.test.tsx` — a module test that needs a real DOM — built by `component()` | the same chromium; no Docker. Runs in its own group, after `website`   |
| `mobile`      | `specs/mobile/**`, built by `mobile()` — serial by default, one driver session per run                                 | Nothing — the Appium protocol double, served once per run              |

Every project the package runs comes from a helper, so `--project api` means the same tree here as in any consumer — `unit()` included. A member without `"type": "module"` writes its config as `vitest.config.mts`: the helpers ship ESM only, a CJS config would have to `require()` them, and `roleOf` already reads `.mts` as the config role — so the rules that judge a config still find it.

Why a file is reached by its ROLE and named by its suffix, and what was weighed against it: [ADR-006](decisions/006-the-catalogue-reaches-a-file-by-its-role.md).

**`specs/lint/` is the lint facet's folder.** Its specs run the plugin, the checker and the preset over fixture TREES, one folder per rule, through `specification.lint()` ([16](16-lint.md)): the rules this package ships are a subject like its binary, and they are specified the way a consumer specifies its own.

**The `unit` project's budget is the whole suite's floor.** It collects the module tests and runs with no service, no browser and no container, so it is the one project a developer runs on every save: the same tree took between nine and eleven seconds on consecutive runs of an idle developer machine, and **the budget a change is designed against is twelve**. It is a design budget, not a gate: wall time is the machine's — the same run takes four times as long on a loaded one — so no check fails on it, and a change that adds a slow file to the project is judged at review against it. The budget sits above the range, not at the best measurement, so a measurement read against it is not read on noise.

Every FACET folder under `specs/` is named for its facet: seven belong to a constructor, and `specs/component/` to the one facet that is a chain — it is the rendered subject this package ships, and its component tests sit beside its components because that is what a rendered unit's test does (`no-unknown-constructor`, `test-beside-its-module`). A probe of a container seam — the postgres and redis handles — is a module against a real service, so it is an integration spec: `specs/integration/services/`, on `specification.integration({ services })` and its one terminal action. What the seam answers BEFORE it reaches a container, and the container adapters the public entry does not publish (`TestcontainersAdapter`, `RunSetupContainer`, `ServiceContainer`), are module tests beside their modules under `src/services/containers/` — a spec reaches the framework through its public entry, and a probe that cannot is telling you where it belongs (the layer map's `architecture/no-framework-internals`, [§ A spec reaches the framework by its entry](#a-spec-reaches-the-framework-by-its-entry)).

```bash
npm test                            # every project — Docker and chromium both required
npx vitest --run --project unit     # the loop: no infrastructure, after npm run build
npx vitest --run --project website  # after npx playwright install chromium
npx vitest --run --project component  # the same chromium, a mounted unit at a time
```

**The mobile tree runs two ways, and the specs are the same both times.** `specs/mobile/` drives Specimen, a small native app. In every run — `make check`, CI — its runner connects to the protocol double in `specs/_shared/_setup/appium/`: a WebDriver server that answers like Appium's XCUITest driver, drawing the app from its description as data (`specs/_shared/_fixtures/specimen-mobile/specimen.ts`). Before a release, or when the appium adapter or the double changes, `make test-mobile` runs the same files against a real iOS simulator and the same app in SwiftUI; no CI job runs it, because CI provisions no simulator. The double proves the facet over the protocol, and only the simulator proves the double tells the truth about a device: a spec green on one and red on the other is a gap in the double. What the target does and needs is `specs/_shared/_fixtures/specimen-mobile/README.md`'s.

A second hole is the RENDERER's, and it is not this repository's to close: a React Native screen never reaches the real Chromium the component facet mounts in, so jest stays on that surface until an experiment rendering it through `react-native-web` shows it can move — [09 — Component specs](09-component.md) lists it with the other three shapes the facet does not take.

## How a spec tree is laid out

The layout is the one the conventions enforce on every consumer (rules `specs-at-declared-depth`, `one-subject-per-spec`, `spec-in-subject-folder`), and this repository is its first consumer — with one difference an application never meets: every app its specs drive is a SPECIMEN, kept as ground under `specs/_shared/_fixtures/`, so every spec here specifies the FRAMEWORK ([23 — Conventions § A specimen's spec](23-conventions.md#a-specimens-spec)), and is filed by the CAPABILITY it asks about rather than by the route, the command or the job it reaches ([§ A specimen's capability folder](#a-specimens-capability-folder)). A facet carries its runners at its ROOT and its tests one folder below, one file per aspect of the capability:

```text
specs/
├── api/
│   ├── api.specification.ts          # runners at the facet root
│   ├── intercepts.specification.ts
│   └── intercept/                    # the capability, named as the matrix names it
│       ├── exhausted.spec.ts         # one aspect asked of it
│       └── _setup/stubs/             # the stubs its specs declare
├── website/
│   └── visit/
└── _shared/                          # what the facets share, in reserved folders alone:
    ├── _fixtures/                    # the specimens and file state, reached by ../../_shared/_fixtures/…;
    └── _seeds/                       # _seeds/, _requests/, _expected/, _setup/ share the same way
```

**The folder names come from the capability matrix below, and nowhere else** — `specimen-filed-by-capability` holds them to it. A capability belongs to no facet in particular, so a facet that gives one a folder calls it by the matrix's name — `specs/api/clock/`, `specs/job/clock/` and `specs/website/clock/` are the same question asked of three constructors, and two names for one capability is the drift a closed vocabulary stops. A facet takes only the capabilities its own column declares: `appium` is mobile's, so the spec of a mobile run's one Appium session sits in `specs/mobile/appium/`, though it runs its vitest projects through the cli runner. It says nothing about where a METHOD may appear: `.seed()` is used inside integration's `call/` scenarios, because seeding is the Given there and not the subject; a capability earns a folder when it is what the specs in it are ABOUT. An integration spec reaches the module of the shared fixtures its chains call (`orders`, whose `stamp` and `tally` are what `clock/` and `table/` call), and is filed the same way. A spec that reaches no specimen is out of that reach, and its folder is its author's: an integration spec calling a module written inline, which this tree never does; integration's seam specs under `services/`, which call the redis or postgres handle itself; and `specs/api/services/initiation-errors.spec.ts`, whose runners never start — each hands a `broken-*` tree to its services as their root, and a root no server command runs from is no app.

The law of the tree — the closed list of `_` folders, `_setup/` for code, the lowest-common placement — is [23 — Conventions § The naming recap](23-conventions.md#the-naming-recap)'s, and this tree follows it: the capability folders' stubs sit in `_setup/stubs/`, and a seed only one facet reads sits in that facet's `_seeds/`. Which of the two legal shapes a given tree takes — its own domain, or sibling tests in a named group folder — is decided by the assets, and that judgement is the process channel's ([23 — Conventions](23-conventions.md)).

The fixture apps the specs drive are SPECIMENS, each named for the facet that drives it, and they follow the placement law like any ground: a specimen one facet reads sits in that facet's `_fixtures/` — `specimen-api-outbound` in api's, `specimen-job` in job's, `specimen-website` and its `specimen-website-backend` in website's, `specimen-cli` and its `-docker`, `-vitest` and `-literate` variants in cli's, `orders`, the module integration's specs call, in integration's, and the `broken-*` trees for the infrastructure failure paths in `specs/api/services/_fixtures/`. The pool, `specs/_shared/_fixtures/`, holds what several facets or a reader outside the specs tree name: `specimen-api` (which carries the jobs too), `specimen-mobile`, which the Makefile runs, `member-workspace`, which lint's module tests, its specs and the checker's command line read, and the trees the lint specs share with the checker's command line — `file-suffix-matches-place-placement`, `no-unused-ground`, `no-unused-ground-ok` and `spec-document-ok`. The code several facets share sits beside the pool, in `specs/_shared/_setup/`: `appium/`, the protocol double the vitest config runs as a global setup, is TypeScript that prepares specs, not data a spec stands on. A lint rule's trees are not in the pool: each rule keeps them in its own `specs/lint/<rule-id>/_fixtures/`, and a tree several rules or the checker's command line read sits in the lowest folder they share.

**The component tree is the one exception, and the exception is the rule it dogfoods.** A rendered unit's test sits BESIDE the unit, so `specs/component/` holds the fixture app and its specs as neighbours. It is not under `_fixtures/`: ground is what a spec stands on from a distance, and here the spec stands next to it. The exception is HELD by rules, not granted by omission: `test-beside-its-module` requires every one of those `.test.tsx` files to have the `.tsx` (or the `.ts` of a hook) of the same basename beside it, and `specs-at-declared-depth`'s row says a `.test.tsx` is out of its reach because a rendered unit never lives in a facet/domain tree.

The tree is filed by capability, the way a specimen's spec is ([§ A specimen's capability folder](#a-specimens-capability-folder)). One test file asks about one capability, and sits with its unit in that capability's folder: a table with a stub in `intercept/`, the project's frame in `wrap/`, a modal hook with its Host in the test in `render/`, a form carrying every verb in `fill/`.

A claim about a second capability goes to that capability's folder, beside a unit of its own. `test-beside-its-module` pairs each test with one unit, so a component that could serve both becomes two small ones: `valued/` and `selected/` each hold a field of their own, rather than rendering `fill/`'s form from across the tree. What a test only passes through is not its capability: the `<StrictMode>` a hook spec renders its Host in is a Given of `render/`, and the target that reaches an element is a means of every folder.

One file still holds more than one: `intercept/page-surface.test.tsx` carries `mockOf` and `waitUntil` beside the module-scope `intercept()`. Neither has a row in the `component` column, so neither has a folder to be filed in.

## The layered reading

The package proves itself in five layers, and they are meant to be read from the inside out: a module against its own exports, a rule against its own fixtures, a facet against its own tree, the built binary against a fixture project, and the CORPUS against what a meta-test says it must keep true. Each layer judges something the one below it cannot — and the meta-tests are counted apart rather than folded into the module tests, because what they judge is the one thing a test beside a module cannot see.

## The lint specs are end-to-end

`specs/lint/**` runs the REAL oxlint, the real checker and the preset's real passes over fixture trees and goldens their whole report, on the lint facet ([16](16-lint.md)). Because the plugins and the checkers load from `dist/`, `npm run build` must precede it — the same ordering `npm run lint` depends on.

A rule is specified in `specs/lint/<rule-id>/<rule-id>.spec.ts` — a folder growing an aspect file of its own when one grows past the line limit — over the trees in its local `_fixtures/`, on one of five runners at the facet root: `lint.specification.ts` (both oxlint plugins, every rule on), `checker-lint.specification.ts` (the conventions checker), `self-lint.specification.ts` (the passes only this package runs), `preset-lint.specification.ts` (the `test()` preset's laws) and `self-preset-lint.specification.ts` (the same preset and this package's own name rule). Every report golden names each finding at its `file:line:column`, then its lesson a part per line; a meta-test holds every rule of the two plugins and every checker pass to a spec there, and every one of them to a golden naming the line and column it fires on. `meta/` holds the reach meta-test, and `kitchen-sink/` the checker's whole-surface regression net.

The checker's own command line — the ratchet, `baseline`, `--member`, `--verbose`, `--format json`, what a document out of its format prints — is a binary, so it is a cli spec: `specs/cli/checker/` and `specs/cli/baseline/`, on `specs/cli/checker-cli.specification.ts`, whose goldens are the exact streams the checker prints.

## Coverage is a ratchet, not a threshold

`npx vitest --run --coverage` turns on v8 — the runtime's own counter, so there
is no instrumentation pass and the numbers do not move when the bundler does —
and writes three reports where the preset sends them ([02 — Developing §
Artefacts live under `.artifacts/`](06-setting-up.md#where-a-run-writes)):
`text` for the person who ran it, `html` for the one chasing a line, and
`json-summary`, which is the one a machine reads.

The count includes the child processes the suite spawns: a document that runs
`checker .` runs `dist/checker.js` in a child, and this repository's
`vitest.config.ts` turns on `autoAttachSubprocess`, so v8 merges what every
child executed. The build writes source maps, which take each bundle back to
the `lint/` and `src/` modules it was built from; `dist/` itself is judged
only after that remap, so no bundle is ever counted as a file of its own.

`npm run coverage` records where the suite stands in `jterrazz.baseline.json`'s
`test.coverage` section, a floor this repository's own `self()` preset
declares beside `test()`, since no consumer runs this gate;
`npm run coverage:check` refuses a run that fell below it. Neither runs the
suite: both read the report of the LAST `--coverage` run, which is why
`make test` runs the suite WITH coverage (`npm test -- --coverage`) before the
gate — a plain `npm test` would leave it judging an older run, or, on a fresh
clone where `.artifacts/` does not exist yet, nothing at all. That target is
the one CI calls ([What CI runs](#what-ci-runs)), so the floor is judged on
every push. It only ever rises: lowering it is an edit to a committed file,
with a commit body saying why.

### One floor, over the whole suite

The baseline is keyed by scope and the CLI
takes `--scope`, so a project can keep its own; this repository records `all`
and nothing else, because the projects overlap — the browser projects and the
node ones both execute `chain/` and `expectations/`, and a floor per project would sum to more than the tree
and ratchet on which project happened to run. A scope missing any of the four
metrics is refused rather than read as a zero, since a floor of zero forbids
nothing.

### Why a ratchet and not a threshold

A fixed threshold would be a number somebody picked. Set it where the project
stands and it forbids nothing; set it where the project should be and every run
is red until it gets there, which is how a gate becomes something people pass
with `--no-verify`. A ratchet asks the only question a gate can answer
honestly: is this change worse than the last one?

### What the report excludes

What the report EXCLUDES is the shape of the answer, not a way to raise the
number: `node_modules/` (Browser Mode instruments the page's bundle, and
react-dom alone is 19 000 statements), `specs/` and `_fixtures/` (a spec is a
test and the app it drives is ground), the type-only and config files.

## Modules with no sibling test

`test-beside-its-module` says a module test lives beside its module. It never said every module has
one, and it cannot: a barrel executes nothing, a `*.port.ts` declares a shape,
and a facet's constructor is proven by the tree that constructs it. What was
missing is the LIST of the ones that do not, and why — a module with real
behaviour, no sibling test and nobody able to say what covers it is the silence
this section closes.

`lint/self/corpus/siblingless-kinds.ts` declares the kinds, each naming the PATHS it claims —
never a prefix, because a kind claiming `src/stubs/` would claim every module
written there next year and `siblingless-module-declared` would be a poster. **`siblingless-module-declared`** fails on a module that
matches none of them, which is what makes a new, unclaimed module fail the
suite on the day it lands.

**`definition-is-its-module`** reads the same kinds. A capability or an action definition passes with
no test beside it only when a kind claims its module, so the exemption has one
owner and the two gates cannot disagree.

## The mutants no test kills

`make mutation` measures the module tests alone ([02 — Developing](02-developing.md)). `make mutation-specs MUTATE=<file>:<from>-<to>,…` measures the whole suite: it builds the instrumented sources, runs every node project against each mutant, and hands the active mutant to every process a spec spawns (`specs/_shared/_setup/mutation/active-mutant.ts`). A mutant a child process reaches is covered by no test of the parent, so each mutant runs all 2 570 tests, and the target is pointed at ranges rather than at the tree.

When the module tests that restated a spec went, in October 2026, 698 mutants they had killed were left to the specs. The specs killed 654, and a spec or a lint case was written for the gaps among the rest. Those ranges were measured again with `make mutation-specs` on the tree as it stands. ## The capability matrix

The catalogue in [24 — Linting](24-linting.md) answers "which conventions are
mechanized". This answers the other half: for each thing the framework can DO,
which facets declare it, and how many of the package's own test files exercise
it there.

It is generated by `npm run docs` from the facets themselves, the `{{token}}`
list the runner and the checker already share, and a scan of the trees each
column owns. A facet states its own rows through its composition: each
option, setup and action it composes carries the row it answers for, an
action that hands a scenario a visitor carries its verbs and targets too,
and `lint/self/corpus/compositions.ts` lists the seven compositions the matrix reads.
What the libraries own — the goldens, the doubles — is declared in
`lint/self/corpus/facet-matrix.ts`.

A file counts in the column whose tree holds it, and only for what that column
declares: `specs/mobile/appium/session.spec.ts` drives the cli runner, so its
`.exec()`, `.fixture()` and `.env()` fall in cells the mobile column leaves

## The package's own rules

Every row of the rule manifest declares its audience (`RowDocs.audience`, `lint/engine/catalogue/row.ts`). A `consumer` rule is what a project using the package meets, and [24 — Linting § The rule catalogue](24-linting.md#the-rule-catalogue) lists it. A `self` rule holds this package's own suite — its catalogue, its capability matrix, its specimens, its skill, its meta-tests — and is listed here, where the `read:` part of its message routes.

A self rule is wired only where this repository judges itself, never in what the tarball carries. Its row lives in `lint/self/catalogue/manifest.ts`, which no published entry imports: the published code reads the consumer rows of `lint/consumer/catalogue/manifest.ts` alone, so no bundle the tarball carries holds a self row. A self static rule is a rule of the `jterrazz-self` plugin (`lint/self/rules/plugin.ts`, bundled as `dist/self-oxlint.js`), which the `self()` preset hands this repository's `oxlint.config.ts`, and the lint specs load beside the published plugin; its findings read `jterrazz-self(<rule>)`. A self checker pass runs in `dist/self.js check` (listed by `lint/self/checks/checker.ts`, composed by `lint/self/self-cli.ts`) — over every specs tree, and over the project's own `src/` and `lint/` — which `npm run lint` calls after the published checker and `files` leaves out; `dist/checker.js` imports nothing of it. A self meta row is a meta-test of this suite, and a self process row is this repository's review. `rule-declares-its-audience` packs the tarball, extracts it, and holds that none of this reaches it: no byte of it names a self row, no entry it publishes registers one, no bin it publishes runs one.

A rule that is both is two: its consumer half ships, its self half stays home. `message-has-four-parts` is the pattern: the four-part form every message takes is the consumer's, stated in [24 — Linting § What a finding says](24-linting.md#what-a-finding-says); the meta-test that holds this catalogue's messages to that form is `message-has-four-parts`, below.

### A spec reaches the framework by its entry

A spec under `specs/` reaches the framework through `@jterrazz/test`, as a consumer does, and so specifies what a consumer installs: the package resolves its own name to its build (`npm run build` first) — node's projects through the exports map, the component project through its alias to `dist/browser/index.js`, the scratch projects a spec runs vitest over through the built entries `specimen-cli-vitest/vitest.sh` hands them. A spec importing its own app's source is the documented pattern and passes, and a `@jterrazz/test/<subpath>` import is `no-unpublished-subpath`'s. A probe that cannot reach its subject through the public entry is a module test beside its module. The edge is judged on the resolved graph by the layer map `jterrazz.config.ts` hands `@jterrazz/typescript`'s Architecture pass — `no-framework-internals` in `ARCHITECTURE` (`lint/self/checks/architecture.ts`) — and prints as `architecture/no-framework-internals` at its import.

### Retro-propagation

Every defect class discovered (review, bug, migration) grows, **in the same change**, the guard that stops it recurring — a static rule, a meta-test, or a runtime error — or an explicit note of why no channel is possible (e.g. "redundant test" is a human judgement). This is the rule that keeps the other seven channels growing instead of decaying. When a defect class is mechanizable, its row joins `lint/consumer/catalogue/manifest.ts` — `lint/self/catalogue/manifest.ts` for a rule only this package is held to — and the catalogue regenerates.

Whether a defect is a CLASS is the one judgement here no channel settles: it is a reading of what will happen again. What the machine takes of it is the rest — `cited-rules-exist` to `catalogue-in-english` hold the catalogue complete and true once the row is written.

### A specimen's capability folder

Every app this repository's specs drive is a specimen, so every spec here is one that `one-subject-per-spec` and `spec-in-subject-folder` leave alone ([23 — Conventions § A specimen's spec](23-conventions.md#a-specimens-spec)), and `specimen-filed-by-capability` files it instead. Its folder is the CAPABILITY it asks about, one below its facet: `specs/api/seed/files.spec.ts`, never under the route the specimen answers on (`users/list/`). The vocabulary is closed and nobody's to invent: each capability the matrix declares for the facet's own column ([§ The capability matrix](#the-capability-matrix)), the words before its first parenthesis kebab-cased — `seed`, `intercept`, `clock`, `to-match`, `exit-code`. A capability of another column is no folder of this facet: `appium` is mobile's, and never a folder of `cli/`. The file is one ASPECT of the capability — what it does when it works, what it refuses, its edges — never a folder per verb.

The component tree is filed the same way, one level down: every file under `specs/component/` sits in a folder the `component` column names — `specs/component/intercept/post-table.tsx` beside its test, `specs/component/wrap/providers.tsx`. The capability is what the unit's test asks about, not what the unit happens to call.

`one-subject-per-spec` and `spec-in-subject-folder` stay `consumer` whole, their specimen carve-out included: any framework repository that keeps specimen apps meets it, and the published checker judges this repository's specs too. What `specimen-filed-by-capability` took from them is where a specimen's spec is filed, never whether it is one.

## Hunting a flake

A test that fails once and passes on the rerun is chased, never retried: the preset sets `retry: 0`. The gesture is Vitest's `--repeats`, which runs every test of the files it is handed ten times in one process:

```bash
npm run test:repeat -- --project unit lint/self/corpus/type-channel.test.ts
```

It is aimed at named files, not at a whole project. A rule test declares its cases through oxlint's `RuleTester`, which refuses a case it has already seen, so a repeated rule test fails on its second pass whatever the rule does. A test that fails on its own second pass is a defect all the same: it cannot run twice in one process.

One flake is known and not reproduced. In a whole-suite run under `--coverage`, the first few component files have failed on `import('vitest-browser-react')` with a SyntaxError whose token varies (`':'`, `'}'`, `Illegal return statement`, `Undefined label 'a'`), and every later file passed. The page parsed a slice of react-dom's client chunk, not a broken file: fifty-two repeated runs, a probe parsing every optimised dependency the server sent, and `DEBUG=vite:deps` over all of them found no malformed response and no re-optimisation mid-run — so `optimizeDeps.noDiscovery` is not the fix, and would cost a consumer its undeclared CommonJS dependencies. What is left is in the browser (a module compiled while the coverage mode switches) or outside the tree (another process installing or running in the same clone). If it recurs, keep the log, the listing of Vite's dependency cache with its `_metadata.json`, and whether another process ran in the clone.

## Probing the container sweep

[18 — Services § Reused across runs](18-services.md#reused-across-runs-locally) states what the services setup's sweep removes. The probe, run from this repository after `npm run build`, sets up a run that holds the reaper, a run killed with its redis running, and an ended container of a session nobody holds — the next setup's sweep leaves none of them.

```bash
node --input-type=module -e "const { GenericContainer } = await import('testcontainers'); await new GenericContainer('$image').start(); setInterval(() => {}, 1000)" &

sleep 10   # until the holder's container runs
node --input-type=module -e "

let url; await setup({ provide: (_, served) => { url = served; } }, async () => {});
await fetch(url + '/containers', { method: 'POST', body: JSON.stringify({ image: '$image', port: 6379 }) });

kill $holder
```

## What CI runs

The workflow is `.github/workflows/validate.yaml`, on every push to `main` and every pull request, delegating to the shared `validate.yaml` of [jterrazz-actions](https://github.com/jterrazz/jterrazz-actions). It restores `.artifacts/`, then runs `make build`, `make lint` and `make test` in that order, with chromium provisioned because the website specs drive a real browser. The same three targets are what a local run owes before a push; the ordering is not decorative, since lint loads what build produced.

**`make test` carries the floor.** It runs the suite WITH coverage and then `npm run coverage:check`, so the ratchet is judged on every push rather than trusted to whoever remembered to type `make check` — a gate CI never runs is a courtesy, not a gate. `make check` is still the whole verdict locally: build, lint, then that same target.

**A run can be split.** `make test SHARD=<index>/<count>` runs one shard of the suite with coverage, and writes its blob report to `.artifacts/vitest/blob/blob-<index>-<count>.json` — the preset names the blob for its shard, so the shards of one run land side by side. A shard judges neither the coverage floor nor the route ratchet, since its coverage and its requests are a part of the run's: it writes its route ledgers to `.artifacts/vitest/routes/shard-<index>-<count>/` and prints `api routes: not judged`. `make test-merge`, run once every shard's blob is in that folder, reads them back as one run with coverage, judges the floor on it, then judges the routes over every shard's ledgers (`node dist/route-split.js`, since a merge runs no global teardown). It reads every blob and every shard's ledgers, so both folders must hold one split's shards alone: a whole `make test` empties them, and a split with another shard count starts after one, or after `rm -rf .artifacts/vitest/blob .artifacts/vitest/routes`. A merge that finds no shard's ledgers at all fails instead of passing unjudged: the shards never ran, or a whole run emptied their folders since. A shard run with `-t` leaves a `partial` mark in its folder, and the merge of a split holding one prints `api routes: not judged`, naming it, since it reached only some routes. Each shard empties its own ledger folder before it runs, as it overwrites its own blob: vitest runs no global setup for a shard that holds no api file, and the folder would keep an earlier split's ledgers. A clone that still holds the `blob` FILE an earlier preset wrote there has it removed by the first shard. The shared workflow does not split the run: it has no shard input.

## Pitfalls

- **Running the lint specs on a stale `dist/`.** `specs/lint/**` and `oxlint.config.ts` both load `dist/oxlint.js`. Without `npm run build`, the specs judge the previous build's rules and report a green that means nothing.
- **Hand-editing a report golden.** A lint spec's report and the checker's streams under `specs/cli/checker/` are the real output. Change the message in the code and regenerate with `TEST_UPDATE=1`; a hand-tuned golden asserts your typing, not the linter's output.
- **Expecting `npm test` to pass with Docker stopped.** Only `unit` and `cli` are infrastructure-free. The Docker-backed tests self-skip inside them, but `api`, `job` and `integration` fail honestly.
- **Adding a test at a facet root.** `specs/<facet>/<aspect>.spec.ts` is refused by `specs-at-declared-depth` in this repository's default depth — the runner lives at the root, the tests live one level down.
- **Writing a facet spec with the unit’s suffix.** `file-suffix-matches-place` refuses it and `jterrazz-test-check specs --fix` renames it with `git mv` — and names every `include`/`exclude` entry of the member the rename broke — the globs whose prefix covers a file it moved and the literals naming one — since an entry the rename leaves behind collects nothing and the run stays green with fewer files. The reverse — a `.spec.ts` with no `specs/` ancestor — is the member pass's finding.
