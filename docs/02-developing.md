# 02 — Developing

How a change to this repository is made: the toolchain, the order its gates demand, which file a change opens and what it owes when it lands. How a consuming project installs and configures the framework is [06 — Setting up a project](06-setting-up.md).

## The loop

The repository answers six `make` targets, the same six every repository of its author answers:

| Target         | Does                                                                                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `make install` | Install the dependencies (`npm ci`, again only when the lockfile moves)                                                                                                        |
| `make build`   | Build the bundle — before `lint` and before the `unit` project; an unchanged tree restores it from the build cache instead                                                     |
| `make lint`    | Typecheck, lint, format check, knip, then the conventions checker and the self checker (the source tree's structure locks)                                                     |
| `make fix`     | Build, then `npx typescript fix`, which runs the conventions' fixes and the self checks first, then oxlint's and the formatter, so the formatter formats what the checks wrote |
| `make test`    | Every suite, with coverage, then the coverage floor                                                                                                                            |
| `make check`   | The whole verdict: build, lint, test                                                                                                                                           |

Every target installs first. CI calls `build`, `lint` and `test` ([03 — Testing § What CI runs](03-testing.md#what-ci-runs)).

The everyday loop and the targets no flow calls:

| Gesture                                         | Does                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `npx vitest --run --project unit`               | The fast suite, with no infrastructure                                                                                                                                                                                                                                                                                                                                        |
| `npm run docs`                                  | Regenerate the generated tables                                                                                                                                                                                                                                                                                                                                               |
| `make test-changed`                             | Only the tests the uncommitted changes reach (`vitest --changed`): the local loop, never a verdict. Like any partial run, it judges no route ratchet ([12 — API](12-api.md#when-a-run-is-not-judged))                                                                                                                                                                         |
| `make test-mobile`                              | The mobile specs on a real iOS simulator, which no CI job provisions; [03 — Testing](03-testing.md) says when it is owed                                                                                                                                                                                                                                                      |
| `make check-links`                              | Every link of `README.md`, `docs/` and `skills/`, remote ones included, with [lychee](https://lychee.cli.rs). It needs the network and a lychee on the machine, and fails where there is none. Never part of `check`: the gate reads local links offline, as `@jterrazz/typescript`'s Markdown pass states                                                                    |
| `make test-merge`                               | Read the blob reports of a sharded run back as one, then judge the coverage floor and the route ratchet on it ([03 — Testing § What CI runs](03-testing.md#what-ci-runs) says how a run is split)                                                                                                                                                                             |
| `make mutation`                                 | [Stryker](https://stryker-mutator.io) over `src/` and `lint/` against the `unit` project: the module tests' mutation score, a measure and never a gate. It rewrites the sources in place for the whole run, so nothing else runs beside it, and leaves its report in `.artifacts/stryker/`, which git ignores. The specs drive the build, which no mutant of this run reaches |
| `make mutation-specs MUTATE=<file>:<from>-<to>` | The suite's score, the specs and the processes they spawn included, over the ranges `MUTATE` names; what it leaves alive is [03 — Testing § The mutants no test kills](03-testing.md#the-mutants-no-test-kills)                                                                                                                                                               |

The `sqlite()` specs of the `unit` project need no rebuild after `npm ci`: this repository runs the `better-sqlite3` line whose native binding ships prebuilt — [06 § What to install](06-setting-up.md#what-to-install) says which line that is, and what an older one costs.

## The build comes first

`oxlint.config.ts` loads this package's OWN plugin from `./dist/oxlint.js`, and the end-to-end lint specs load it too. Node's type-stripping does not resolve a `.js` specifier back to its `.ts` source, so **`npm run build` must precede `npm run lint`** and must precede the `unit` project. A lint run on a stale bundle judges the previous build's rules.

`make build` runs that build through Turborepo, whose cache is keyed by the content of what the bundle is made of: every file git tracks or would track, less `docs/`, `specs/`, `skills/`, the Markdown and the test files. An unchanged tree restores `dist/` from `.artifacts/turbo/` rather than bundling again, so `make fix`, `make check`, `npm run docs` and `npm run coverage` pay the build once per change. All four take one path, `npm run build:cached`, which also turns Turborepo's telemetry off. `turbo.json` states those inputs; Turborepo's per-task log lands in `.turbo/`, which it offers no key to move, and `.gitignore` holds it.

The key reads the lockfile, not the installed toolchain. On a machine that develops the toolchain beside this package, with `@jterrazz/typescript` installed from a sibling checkout (`file:../package-typescript`), it is locked by version alone, so a preset change reinstalled at the same version leaves the key unchanged, and `make build` restores a bundle built under the old `compilerOptions`. After such a reinstall, run `npx turbo run build --force` or `rm -rf .artifacts/turbo`. A restore only adds files, so `npm run build:cached` removes `dist/` first: nothing left there by another branch survives into the bundle or a local `npm pack`.

This repository's `jterrazz.config.ts` lists the presets it is held to — `typescript({ profile: 'node' })` and `test()`, as every consumer does ([24 § What the preset carries](24-linting.md#what-the-preset-carries)), then `self()`, the one preset only this repository declares — and adds only the `schema/` root and, under `optOuts`, the base law it sets aside, with its reason. `self()` is `lint/self/preset.ts`, built as `dist/self-config.js`, and it carries everything this repository adds to its own tree: its layers, `ARCHITECTURE` in `lint/self/checks/architecture.ts`, which compiles `FRAMEWORK_LAYERS` (`lint/self/checks/layers.ts`) and the library owners into dependency-cruiser rules — the enforced statement of the trees [01 — Architecture](01-architecture.md) describes, the direction of `lint/` being the base preset's; the one name rule only this repository is held to ([03 — Testing](03-testing.md#the-packages-own-rules)); the self plugin and its rules; and the coverage floor, the `test.coverage` section of the baseline. Its `oxlint.config.ts` is `fromPresets(settings)` and the repository's own overrides.

## What a change owes

Four things land in the SAME commit as the change that makes them true.

- **The guard.** Every defect class discovered — in review, from a bug, during a migration — grows the thing that stops it recurring: a static rule, a meta-test, or a runtime refusal. It is what keeps the other channels growing instead of decaying. When no channel is possible, the change says so explicitly.
- **The regenerated tables.** `npm run docs` rewrites every `GENERATED` block at once — in [03 — Testing](03-testing.md) the layered reading (`layers`), the siblingless table (`siblings`), the capability matrix (`matrix`), the meta-test channel (`meta-tests`) and the package's own rules (`self-rules`); the rule catalogue in [24 — Linting](24-linting.md) (`catalogue`); the fork in [05 — Getting started](05-getting-started.md) (`fork`) — and `schema/spec.schema.json`. Never edit one by hand: the freshness meta-tests fail on a hand edit.
- **The chapter the behaviour falsified.** A page that still describes the old behaviour is a defect that ships. The corpus is mapped by [`docs/README.md`](README.md).
- **The skill, when the public surface moved.** `skills/jterrazz-test/SKILL.md` is hand-written and short — which kind, the pitfalls, the chapter to read next — and a meta-test fails when it names a symbol the entries do not export or a chapter that is not on disk; `README.md` is the front page and moves with a public API change too.

## The oxlint plugin API is alpha

Oxlint's JS-plugin API is **alpha**. The plugin takes oxlint's types from `@oxlint/plugins` — the context, the report, the fixer, the comments, a node's span — and keeps one view of its own (`lint/kit/project/rule.ts`): a rule reads a node by its `type` and its span, every other field defensively, so a change to oxlint's generated ESTree union is not a change to the rules. Every rule is written in oxlint's `createOnce` form: its visitor is built once per run, and its `before` hook resets what the rule keeps for one file and returns `false` for a file the rule does not judge, which oxlint then skips. What every rule asks of a file — its role, whether it is production, its `specs/` anchor — is answered once per file for all of them (`lint/kit/project/linted-file.ts`). `lint/self/corpus/rule-state.test.ts` holds each rule to both: no state a `before` leaves unreset, and the same verdicts from a file linted alone or after the rest of its corpus. Expect to re-validate the plugin on oxlint majors; the E2E specs (`specs/lint/**`, one violation/compliant fixture pair per rule) run the real binary and are the canary.

## Pitfalls

- **Linting before building.** The lint loads this package's own plugin from `dist/`, so a lint on a stale bundle judges the previous build's rules ([The build comes first](#the-build-comes-first)).
- **Editing a generated table by hand.** The next `npm run docs` overwrites it, and the freshness meta-test fails until it does ([What a change owes](#what-a-change-owes)).
- **A stale plugin in the editor after a rebuild.** The oxlint language server loads `dist/oxlint.js` once and keeps it for the life of the server, so after `npm run build` the editor still lints against the old bundle. The command line is authoritative; restart the editor's oxlint server to resync.
- **Restoring a bundle built under an old toolchain.** The build cache keys on the lockfile, not on the installed `@jterrazz/typescript`; after reinstalling a sibling checkout at the same version, run `npx turbo run build --force`.
