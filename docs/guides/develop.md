# Develop

How a change to this repository is made: the toolchain, the order its gates demand, which file a change opens and what it owes when it lands. How a consuming project installs and configures the framework is [Set up a project](../start/set-up-a-project.md).

## The loop

The repository answers six `make` targets, the same six every repository of its author answers:

| Target         | Does                                                                                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `make install` | Install the dependencies (`npm ci`, again only when the lockfile moves)                                                                                                        |
| `make build`   | Build the bundle, before `lint` and before the `unit` project; an unchanged tree restores it from the build cache instead                                                      |
| `make lint`    | Typecheck, lint, format check, knip, then the conventions checker and the self checker (the source tree's structure locks)                                                     |
| `make fix`     | Build, then `npx typescript fix`, which runs the conventions' fixes and the self checks first, then oxlint's and the formatter, so the formatter formats what the checks wrote |
| `make test`    | Every suite, through `npx typescript test`, which answers a tree it already proved green from that proof                                                                       |
| `make check`   | The whole verdict: build, lint, test, then the mutation verdict (`make mutation`, incremental); a stage whose inputs it already proved green answers from its proof            |

A stage keeps its green as a proof keyed by the content of everything it reads, under `.artifacts/proven/`, and answers the same key from it: `make lint`, `make test` and `make mutation` run nothing on a tree they already proved green, on a laptop as on a runner ([the toolchain's Quality checks § A tree proven green](https://github.com/jterrazz/package-typescript/blob/main/docs/reference/quality-checks.md#a-tree-proven-green)). `check` asks no stage cold; a run that must ignore its proofs says so itself, `make mutation MUTATION_ARGS=--cold`.

Every target installs first. CI calls `build`, `lint`, `test`, then `make mutation` ([Test § What CI runs](test.md#what-ci-runs)).

`make mutation` is `typescript mutation`: [Stryker](https://stryker-mutator.io), from the config the toolchain derives with `typescript.mutation`, twice. The first run is the `unit` project over `src/` and the shipped `lint/` code that carries a module test; the second is every node project, against a build of the instrumented sources, over every mutant the module tests let live and the changed lines (the change not yet committed or, on a clean tree, the branch since its merge-base with the default branch) that no module test runs. Every process a spec spawns is handed the active mutant. It fails on any mutant a test runs and none detects ([its verdict](https://github.com/jterrazz/package-typescript/blob/main/docs/reference/quality-checks.md#every-mutant-a-test-runs-is-detected)). `lint/self/` is not mutated: its audits run over this repository's own corpus, which they hold clean, so a mutant that loosens one survives by construction. A run mutates a sandbox copy under `.artifacts/stryker/tmp/`, never the checkout, and leaves its reports in `.artifacts/stryker/`, which git ignores.

It is incremental: Stryker re-runs only the mutants whose source or tests changed since the report it left, so a run over a day's changes takes roughly two to four minutes, and a first module run in a fresh clone, with no report yet, takes 75 minutes, once ([measured by ADR-020](https://github.com/jterrazz/package-typescript/blob/main/docs/decisions/020-mutation-measures-the-whole-suite-over-a-change.md#consequences)). A survivor whose covering test was removed keeps its result until its source changes, so a report that disagrees with a fresh read is cleared by deleting `.artifacts/stryker/incremental.json`, and `.artifacts/stryker/suite-incremental.json` for the suite's, whose stale entries the suite run reuses.

The everyday loop, and the targets beyond the six:

| Gesture                           | Does                                                                                                                                                                                                                                                                                                       |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `npx vitest --run --project unit` | The fast suite, with no infrastructure                                                                                                                                                                                                                                                                     |
| `npm run docs`                    | Regenerate the generated tables                                                                                                                                                                                                                                                                            |
| `make test-changed`               | Only the tests the uncommitted changes reach (`vitest --changed`): the local loop, never a verdict. Like any partial run, it judges no route ratchet ([API specs](api-specs.md#when-a-run-is-not-judged))                                                                                                  |
| `make test-mobile`                | The mobile specs on a real iOS simulator; no CI job runs it, and [Test](test.md) says when it is owed                                                                                                                                                                                                      |
| `make check-links`                | Every link of `README.md`, `docs/` and `skills/`, remote ones included, with [lychee](https://lychee.cli.rs). It needs the network and a lychee on the machine, and fails where there is none. Never part of `check`: the gate reads local links offline, as `@jterrazz/typescript`'s Markdown pass states |
| `make test-merge`                 | Read the blob reports of a sharded run back as one, then judge the route ratchet on it ([Test § What CI runs](test.md#what-ci-runs) says how a run is split)                                                                                                                                               |
| `make rehearse`                   | The release gate on Linux, on the commit to tag, before the tag ([Releasing](release.md) says when). It needs docker and the network; never part of `check`                                                                                                                                                |

The `sqlite()` specs of the `unit` project need no rebuild after `npm ci`: this repository runs the `better-sqlite3` line whose native binding ships prebuilt. [Set up a project § What to install](../start/set-up-a-project.md#what-to-install) says which line that is, and what an older one costs.

## The build comes first

The lint loads this package's OWN plugin and presets from its build (`test()` from `dist/config.js`, the plugin from `dist/oxlint.js`, `self()` and its checks from `.artifacts/dev/`), and the end-to-end lint specs load them too. Node's type-stripping does not resolve a `.js` specifier back to its `.ts` source, so **`npm run build` must precede `npm run lint`** and must precede the `unit` project. A lint run on a stale bundle judges the previous build's rules.

`npm run build` is `typescript build`: the toolchain derives the bundle from the manifest (every `exports`, `imports` and `bin` target from its source) and from the names of the modules loaded by path: each `*.global-setup.ts` a specification hands vitest is shipped in `dist/` under its own name, and the programs only this repository runs (each `*.cli.ts`: `schema`, `route-split`, `self`; and the modules at the root of `lint/self/`: `preset`, `plugin`) are built into `.artifacts/dev/` and never shipped.

This repository's presets are its own build, and the build reads `jterrazz.config.ts` before there is one: the file lists `test()` and `self()` through `ownPresets` ([`@jterrazz/typescript`'s Configuration](https://github.com/jterrazz/package-typescript/blob/main/docs/reference/configuration.md#a-repository-held-to-its-own-presets)), so a fresh clone's first build reads the declaration alone, and every later run reads the presets too. Any other command over an unbuilt tree (a lint, a test, an editor's language server) is refused in four parts naming `npm run build`, so none of them passes on nothing.

This repository's `jterrazz.config.ts` declares it a `library` on `node`, lists `test()`, as every consumer does ([Linting § What the preset carries](../reference/linting.md#what-the-preset-carries)), then `self()`, the one preset only this repository declares, and states only its exceptions (how four test projects depart from the ones its tree derives, a mutation exclusion, the lint rules it sets apart, the `schema/` root), each with its reason, and under `optOuts` the two laws it sets aside: a base law, and its own preset's network seam, since the module test of the handlers that wrap msw drives msw itself; `self()` restates that seam's law for every other test file of the repository. `self()` is `lint/self/preset.ts`, built as `.artifacts/dev/preset.js`, and it carries everything this repository adds to its own tree: its layers, `ARCHITECTURE` in `lint/self/checks/architecture.ts`, which compiles `FRAMEWORK_LAYERS` (`lint/self/checks/layers.ts`) and the library owners into dependency-cruiser rules: the enforced statement of the trees [Architecture](../concepts/architecture.md) describes, the direction of `lint/` being the toolchain's standard's; the one name rule only this repository is held to ([Test](test.md#the-packages-own-rules)); the self plugin and its rules. Its `oxlint.config.ts`, `oxfmt.config.ts`, `tsconfig.json` and `vitest.config.ts` are the lines the toolchain derives.

## What a change owes

Four things land in the SAME commit as the change that makes them true.

- **The guard.** Every defect class discovered (in review, from a bug, during a migration) grows the thing that stops it recurring: a static rule, a meta-test, or a runtime refusal. It is what keeps the other channels growing instead of decaying. When no channel is possible, the change says so explicitly.
- **The regenerated tables.** `npm run docs` rewrites every `GENERATED` block at once, and `schema/spec.schema.json`. The blocks are, in [Test](test.md), the layered reading (`layers`), the siblingless table (`siblings`), the capability matrix (`matrix`), the meta-test channel (`meta-tests`) and the package's own rules (`self-rules`); the rule catalogue in [Linting](../reference/linting.md) (`catalogue`); the fork in [Getting started](../start/getting-started.md) (`fork`). Never edit one by hand: the freshness meta-tests fail on a hand edit.
- **The chapter the behaviour falsified.** A page that still describes the old behaviour is a defect that ships. The corpus is mapped by [`docs/README.md`](../README.md).
- **The skill, when the public surface moved.** `skills/jterrazz-test/SKILL.md` is hand-written and short (which kind, the pitfalls, the chapter to read next), and a meta-test fails when it names a symbol the entries do not export or a chapter that is not on disk; `README.md` is the front page and moves with a public API change too.

## The oxlint plugin API is alpha

Oxlint's JS-plugin API is **alpha**. The plugin takes oxlint's types from `@oxlint/plugins` (the context, the report, the fixer, the comments, a node's span) and keeps one view of its own (`lint/kit/project/rule.ts`): a rule reads a node by its `type` and its span, every other field defensively, so a change to oxlint's generated ESTree union is not a change to the rules. Every rule is written in oxlint's `createOnce` form: its visitor is built once per run, and its `before` hook resets what the rule keeps for one file and returns `false` for a file the rule does not judge, which oxlint then skips. What every rule asks of a file (its role, whether it is production, its `specs/` anchor) is answered once per file for all of them (`lint/kit/project/linted-file.ts`). `lint/self/corpus/__tests__/rule-state.test.ts` holds each rule to both: no state a `before` leaves unreset, and the same verdicts from a file linted alone or after the rest of its corpus. Expect to re-validate the plugin on oxlint majors; the E2E specs (`specs/lint/**`, one violation/compliant fixture pair per rule) run the real binary and are the canary.

## Pitfalls

- **Linting before building.** The lint loads this package's own plugin from `dist/`, so a lint on a stale bundle judges the previous build's rules ([The build comes first](#the-build-comes-first)).
- **Editing a generated table by hand.** The next `npm run docs` overwrites it, and the freshness meta-test fails until it does ([What a change owes](#what-a-change-owes)).
- **A stale plugin in the editor after a rebuild.** The oxlint language server loads `dist/oxlint.js` once and keeps it for the life of the server, so after `npm run build` the editor still lints against the old bundle. The command line is authoritative; restart the editor's oxlint server to resync.

## Writing the manual

The manual is cut into the four sections the [map](../README.md) lists; how a page is written:

- **One owner per fact.** Each fact is stated on one page; the others link to it.
- **The kind guides share one outline** (what it specifies, the constructor, the chain, the result, unique here, pitfalls), so the reader who learned one kind knows where to look in the next.
- **Rules live in the code.** A rule's normative sentence is written in `lint/consumer/catalogue/manifest.json` and generated into [Linting](../reference/linting.md); the pages explain and illustrate, and the catalogue decides.
- **Every example compiles.** A meta-test typechecks each block that imports only the framework, so a sample cannot drift from the API.
- **A block that starts at `test(...)` is an excerpt.** In its file, that test sits inside the file's one `describe`, which a block showing a whole file writes out.
