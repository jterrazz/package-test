# Architecture

How the package is built: the runner model every kind of test shares, the source trees and the one direction their imports go, the channels a convention is enforced through, and what the tarball publishes. What a test looks like from the outside is [Getting started](../start/getting-started.md); this page is for changing the package.

The rules themselves — what they say and why — are [Conventions](conventions.md); their normative sentences are the generated catalogue, [Linting](../reference/linting.md).

## The runner model

Every specification — the code behind one kind of test — is the same four steps. A **constructor** takes options and returns a **handle**; the handle opens a **chain** of zero or more setups closed by exactly one terminal action; the action executes and resolves to a **typed result**; the result is asserted through vitest's `expect()`. Nothing else is public — there is no imperative escape hatch, because a spec that can do anything proves nothing in particular.

Seven constructors exist and the list is closed (`src/specifications/specification.ts`):

| Constructor                   | Handle destructures to      | Subject under test                               |
| ----------------------------- | --------------------------- | ------------------------------------------------ |
| `specification.api()`         | `{ api, cleanup, docker }`  | An HTTP API, built and served in this process    |
| `specification.job()`         | `{ job, cleanup }`          | A background pipeline, triggered by name         |
| `specification.cli()`         | `{ cli, cleanup, docker }`  | A command binary in a fresh temp directory       |
| `specification.integration()` | `{ integration, cleanup }`  | A module against real services, or a golden      |
| `specification.website()`     | `{ website, cleanup, url }` | A rendered page — fetched, or driven in chromium |
| `specification.mobile()`      | `{ mobile, cleanup, udid }` | A native screen on an iOS simulator              |
| `specification.lint()`        | `{ lint, cleanup }`         | The rules a project ships, over a fixture tree   |

The asymmetry in that column is the model, not an oversight: `docker` reads a container the subject itself started, and neither a pipeline triggered by name nor a module called in-process is specified by the containers it starts, so `job` and `integration` are handed none; `website` and `mobile` drive a browser and a simulator rather than an orchestrated stack, so they carry neither; and `lint` starts nothing at all, its `cleanup` releasing nothing.

**One specification has no constructor**, and the same reason explains it: a rendered component starts nothing. `component` ([Component specs](../guides/component-specs.md)) is a chain the package exports directly — `component.intercept(…).render(<X />)` — so there is no handle to destructure and no `cleanup` to pass to `afterAll`. What every render of a project shares (the providers, the Vite pipeline, the viewport) is the PROJECT's, stated once by `component()` in `vitest.config.ts`.

A runner is created **once per suite**, in a `*.specification.ts` file, and imported by the test files beside it. That split is what makes the container lifecycle affordable — one Postgres per suite, not one per test — and it is why `afterAll(cleanup)` belongs in the specification file and nowhere else.

### The seam under the chain

A specification's chain is COMPOSED: `src/specifications/<specification>/<specification>.composition.ts` lists the setups (each a `*.capability.ts`) and the terminal actions (each a `*.action.ts`) it is made of and the adapter each one is armed through, `defineSpecification` opens the chain, and every action runs through the one pipeline of `src/chain/perform.ts`. Every specification — `job`, `api`, `website`, `integration`, `cli`, `mobile` and `component` — is composed, and there is no other chain. The infrastructure a chain needs is reached through **ports** — each a `*.port.ts` beside the area or the specification that owns it (`database`, `service`, `container`, `isolation` under `src/services/`; `fixture`, `link` under `src/disk/`; `server`, `cli`, `browser`, `device` in their specification) — and an adapter implements one. So the chain knows "a database exists"; it never knows Postgres.

Every seam is opened lazily rather than imported, and each one is an optional peer loaded by the one module that owns it, so a project that tests no page, no component and no database installs none of them. Which peer each specification and each service needs, and what its refusal says, is [Set up a project § What to install](../start/set-up-a-project.md#what-to-install)'s list; a service's refusal is built by `src/services/peer.ts`, and a specification's by the adapter that loads its peer.

## The source trees

The code is trees with declared, one-directional edges: the product under `src/`, and `lint/` at the repository root beside it — the rules the package ships (the spine: `src/`, `lint/`, `specs/`, `docs/`, `skills/`). The map is the project's to declare, so this package declares its own as `FRAMEWORK_LAYERS` in `lint/self/checks/layers.ts`; `lint/self/checks/architecture.ts` compiles it, with the library owners, the specification faces and the direction of `lint/`, into the dependency-cruiser rules `jterrazz.config.ts` hands the toolchain's Architecture pass, and that declaration is the enforced statement of what follows — each crossing named at its import.

The root reads the sentence of a test. A test opens a **specification** on its subject, sets up what **surrounds** it — the stubs, the services, the disk, the clock, the doubles — has a **visitor** act on it, and judges the result with **expectations**; the **chain** is the machinery that composes all of it, and **vitest** the runner that runs it. Each word is one tree at the root of `src/`, beside the three entries and their tests, and a lock of this repository's own holds the list closed.

Two laws keep the audiences apart, the same in every repository that keeps the tree, and `@jterrazz/typescript`'s Names pass holds both. **Declarations only:** `consumer/` and `self/` hold a rule, a check, a decision on an upstream rule, a catalogue entry, or their tests; a module there hands another module no function but one named for its file, and the code declarations share is `lint/kit/`'s. **The kit knows no declaration:** it is handed the rows, the chapter they are read at, the families and the checks, and an entry at the root of `lint/` — the plugin, the config, the checks — hands them.

An import in `lint/` goes one way: `lint/kit/` imports nothing of `consumer/`, `self/` or an entry at the root of `lint/`; `consumer/catalogue/` only `lint/kit/`, since it is the list every rule and pass reads its sentence from; `self/catalogue/` `lint/kit/` and the consumer catalogue it extends; `consumer/rulebook/`, `consumer/rules/` and `consumer/checks/` the catalogue and `lint/kit/`, never each other; the entry any of them. A catalogue's own tests are test material, and read the declarations they audit. That direction is not this package's to state: it is the law of every `lint/` tree, carried by `@jterrazz/typescript`'s base preset, which the Architecture pass holds this repository to with no line of its own. This repository keeps one difference, set aside in the open under `optOuts` in `jterrazz.config.ts`, with its reason and counted by the drift report: the self folders other than the catalogue read each other — the corpus audits the self checker and plugin by importing them.

`lint/` and `src/` import each other one way only, and a module both need has one owner. The shipped `lint/` never reads the product: what the runner and the lint both read — the ground names, the root walk and the git tree it walks, the yaml document and the `<case>.spec.yaml` grammar, the token kinds, the stub kinds, the relative-path law, the settings file's `test` section, the artefact paths, the route-coverage key, and the four-part lesson a runtime refusal and a finding both print (`refusalBlock` and `refusal` of `@jterrazz/typescript/rules`) — lives in `lint/kit/` or in the kit it builds on. A runtime refusal is the product's own: `src/chain/refusals/` holds `refusal()`, the four-part block the product throws — built from a refusal row's sentence and the catalogue page it is read at, or from a lesson naming the chapter that explains it — `invariant()`, the one message of what only the framework can cause, and `rows.ts`, the refusal rows and the runtime channel of the catalogue, which the chapter projection reads from there. `src/` imports `lint/kit/` and nothing else of `lint/`. `self/`, never shipped, may read `src/`: it judges the repository's own product; the shipped `lint/` never reads `src/`. The same law holds in `@jterrazz/typescript`, whose `src/` is the command that runs its `lint/`, and the base preset carries it for both: `src-reads-no-declaration` and `shipped-lint-reads-no-self`, printed as `architecture/<law>` at the import.

**A setup is defined once, whatever the specification.** A second copy of "declare a stub, seed a table, run the thing" is how two specifications drift, so a specification never implements one: it composes the definition and names the adapter it is armed through, and its chain type is computed from the same list (`src/chain/chain.ts`), each chain published as an interface so a compiler message prints its name. Every specification's `<specification>.composition.ts` names that chain beside its composition, so the specification's own folder says what its constructor hands out; `component`, which has no constructor, is opened once by its own page face, `specifications/component/component.face.browser.ts`, which the page's entry re-exports.

The edges point one way: `chain ← visitor · expectations · stubs · services · disk · clock · mocks ← vitest ← specifications ← the entries` — the machinery at the bottom, the notions of the sentence beside each other and apart, the specifications composing them, the entries publishing the specifications. Some carry their reason in the declaration itself. `expectations/result.ts` reaches `services/database-option` because a table read names its database by the rule a seed names it by. `stubs/` reaches `expectations/tokens/` because a stub's request filter IS an expectation on the outgoing request — one `match.*` and `{{token}}` grammar, never a second. A specification's `<specification>.project.ts` reaches `vitest/project` because the runner config runs only in the Vitest main process, never in test code; `vitest/` knows no specification, so the one vite plugin a specification owns, the cli's literate door, reaches the preset through the entry that composes them. The runner reaches `lint/kit/` for exactly what it shares with the lint — the token list, the ground names, the stub kinds, the root walk and the tree it walks (the kit's git tree: what git does not ignore), the `<case>.spec.yaml` parser — so that the file the lint accepts is the file the runner runs, from ONE parser. The map holds more than the layer edges, each a rule of `ARCHITECTURE` named at its import: a specification never imports another (`specification-imports-no-other-specification`), a concept folder is reached only from inside its specification, the entries through its face (`specification-entered-by-its-face*`), and each third-party library is imported by exactly one slice (`library-*-has-one-owner`: `playwright` by `specifications/website/`, `webdriverio` by `specifications/mobile/`, `msw` by `stubs/delivery/`, `pg` by `services/postgres/` …); a node builtin is no library, and each slice spawns only the program its own concept owns ([ADR-009](../decisions/009-node-builtins-are-not-libraries.md)). What the map cannot express is held by the self checker passes under `lint/self/checks/`, one file per pass over the walk `lint/kit/project/source.ts` shares, each finding at the entry, the import or the folder it names: the source root holds the entries, their tests and the trees of the sentence alone, the stubs are entered by what they publish — a specification reaches a delivery only through an edge `DELIVERY_READERS` declares — and a folder under `src/` is named for a concept, never a role ([Test § The package's own rules](../guides/test.md#the-packages-own-rules) lists each). Swapping the runner would be a rewrite of `vitest/`, its entry, the specifications' projects, the component's page and the few bricks built on a vitest primitive — the clock (`vi`), the scratch directory (`onTestFinished`), the doubles (`vitest-mock-extended`) and the goldens, whose matchers are registered on vitest's `expect` — and of nothing else.

This package's product IS test tooling, so `no-test-code-in-production` — which keeps a consumer's production away from test material — is turned off by path wherever that is the job: `vitest/` and its entry, each specification's project, the run's global setups, the component's page, the website's playwright adapter, the stubs' deliveries (`stubs/delivery/`), the clock, the doubles, the scratch directory, the goldens and update mode. Every other module is held to it — the entries and the specification constructors included, which is why a constructor is named `<specification>.handle.ts` and never by a suffix `no-test-code-in-production` reads as test material; and no module a bundle is built from may be test material, which the `package-exports` meta-test reads from the build's source maps.

The table's May-import column is a reading of `FRAMEWORK_LAYERS`, never a second statement of it: the declaration in `lint/self/checks/layers.ts` is what the Architecture pass enforces and what a change edits. Where a grant names one subpath of a package (`@jterrazz/typescript/config`), the layer is granted the package: dependency-cruiser judges where an import lands, and a package's `exports` land every subpath in the package's own folder — only a subpath that lands in a folder of its own (`vitest/browser`) keeps an owner apart from its package.

There are THREE composition roots and none names a layer. `src/index.ts` is node's: re-exports only — each specification's face (`src/specifications/<specification>/<specification>.face.ts`, the names that specification contributes) and the modules of the other layers by path. `src/index.browser.ts` is the page's: it publishes the node entry's types whole and every value a page can run, refusing the node-only ones — see [What the tree publishes](#what-the-tree-publishes). `src/index.vitest.ts` is the runner config's, `@jterrazz/test/vitest`: it publishes `unit()` and every specification's project beside the preset, derives `vitestConfig` from the declared projects with those helpers, and hands the preset the cli's literate plugin, so `vitest/` never reaches a specification.

## The eight enforcement channels

A convention this package states is held by a **channel**, and every row of the catalogue names exactly one of eight. The guiding aim is that most enforcement is programmatic, not review-borne.

- **static** — the `jterrazz/*` oxlint plugin: one file per rule under `lint/consumer/rules/<family>/`, the folder of its catalogue family — AST analysis, one diagnostic per file.
- **upstream** — a convention an oxlint vitest-plugin rule already holds, set as an OPTION by the `test()` preset rather than duplicated as a rule of ours ([ADR-005](../decisions/005-the-doubles-ladder-is-closed.md)).
- **toolchain** — the import and naming rules the `test()` preset hands `@jterrazz/typescript`'s dependency-cruiser and ls-lint passes, printed as `architecture/<rule>` and `names/<rule>`: a project that declares the preset in its `jterrazz.config.ts` is held to them by `typescript check`.
- **checker** — passes of the conventions checks `test()` brings to `typescript check`, reading what an AST cannot: the `{{token}}` grammar of `_requests/` and `_expected/` fixtures, the `<case>.spec.yaml` document family, cross-file analyses that cross a `*.specification.ts` with its tests, and the member pass that judges a package rather than a tree.
- **runtime** — the framework refuses incorrect usage as it executes, where static analysis abstains (a non-literal argument) or cannot reach (the network, a container lifecycle).
- **type** — what the compiler refuses with no rule at all, proven by a consumer's module compiled against the installed declarations (`specs/cli/tsc/`).
- **meta** — what the framework's own suite holds about itself: the catalogue's freshness, its completeness, the reach of its rules — [Test](../guides/test.md) owns the channel.
- **process** — the judgement no single channel settles: asset-driven grouping, golden-file discipline, retro-propagation.

The channel a rule sits on is not prose here: it is a field of `lint/consumer/catalogue/manifest.ts`, the single source of truth from which the catalogue in [Linting](../reference/linting.md) is generated. So is its audience: a `consumer` rule is what a project using the package meets and is listed there, a `self` rule holds only this package's own suite, has its row in `lint/self/catalogue/manifest.ts`, and is listed in [Test § The package's own rules](../guides/test.md#the-packages-own-rules). A rule and its normative sentence live together in the code, so the two cannot drift.

## What the tree publishes

The bundle is built by `typescript build`, from the manifest and `typescript.build`, into `dist/`, and its shape follows how each entry is consumed. `dist/` carries the entries — `index` and `vitest` ESM-only, since vitest is — plus `checker` (`lint/index.checker.ts`, the `#checker` private import) and the global setups the specifications hand vitest by path; the package ships no CLI. The repository's own programs — `schema`, `route-split` and the `self` program (`lint/self/self-cli.ts`): the self checks `typescript check` runs, the pages and the coverage floor — are built into `.artifacts/dev/` and are absent from `dist/` by construction. The `oxlint` plugin ships dual, because oxlint loads it from a consumer project that may itself be CommonJS.

**There are FIVE entries and no more**: `@jterrazz/test` for everything a spec uses, `@jterrazz/test/vitest` for the project helpers and the `vitestConfig` the derived `vitest.config.ts` awaits, `@jterrazz/test/oxlint` for the lint plugin, `@jterrazz/test/config` for the `test()` preset a `jterrazz.config.ts` lists, `@jterrazz/test/schema` for an editor validating a `<case>.spec.yaml`. That is rule `no-unpublished-subpath` rather than a convention of taste, and the exemption is derived from the manifest's own `exports` map (the kit's `declaredSubpaths`), so a subpath is exempt the moment it is published and stops being exempt the moment it is withdrawn.

**The root entry has two runtimes.** A component test renders in a real browser, and the node entry cannot load there: it imports node builtins at load — `node:fs` and `node:child_process` among them — while the native seams (`pg`, `better-sqlite3`, `testcontainers`) are lazy peers, opened on first use. So `exports["."]` carries a `browser` condition resolving to `dist/browser/index.js` — the same public surface, built for a page, where every node-only name (the seven constructors, `ruleTester()`, the services, the docker accessors, the results that walk a disk) is a stub that throws where it was called, naming the specification and saying it runs under node. The split is the RUNTIME's and never the specifications': one specifier, so no spec has to remember which entry it may import.

`types` is stated once, and it is the node build's — so the two runtimes are ONE type surface and a name cannot exist on one side only. The page's entry takes its types from the node's (`export type *`), so they cannot drift, and `specs/cli/node/names.spec.ts`, over the packed tarball, records both builds' names and fails a value the page build lacks.

The API is the types the package publishes, and nothing re-states it. What the code does project into the corpus is a set of generated tables and `schema/spec.schema.json`, generated from the document grammar's own constants; which tables, and the one gesture that writes them, is [Develop § What a change owes](../guides/develop.md#what-a-change-owes)'s list. Both `docs/` and `schema/` ship in the tarball, `docs/` less the two pages that are this repository's own, so a consumer reads the manual where the messages send them, inside the install ([Release](../guides/release.md#what-leaves-the-tree) names the two). All of them are held fresh by meta-tests.

## Pitfalls

- **Reaching for a dependency from `chain/`.** A new external package belongs to the ONE slice that needs it — a notion (`stubs/`, `services/` …) or a specification — and nowhere else. Only a library every layer truly shares sits behind the chain, in the one folder `FRAMEWORK_LAYERS` grants it to: vitest's test hooks in `paths/`; the `yaml` library and the toolchain's config types sit in `lint/kit/project/`, which the chain reaches. Anything else the chain imports is the boundary this package cannot afford to blur, and the layer map and the library-ownership rules refuse it.
- **Adding an eighth constructor.** The seven are the closed vocabulary the conventions, the linter and the documentation are all shaped around. A new SUBJECT to specify is a design decision, and it earns a record in [`decisions/`](../decisions/) before it earns a constructor — as `integration` did in [ADR-004](../decisions/004-a-module-against-real-services-or-a-golden-is-the-integration-specification.md) and `lint` in [ADR-015](../decisions/015-a-rule-a-project-ships-is-the-lint-specification.md).
- **Writing a rule's normative sentence into a chapter.** It belongs in `lint/consumer/catalogue/manifest.ts` beside the implementation; a chapter that restates it is the second copy the whole design exists to prevent.
