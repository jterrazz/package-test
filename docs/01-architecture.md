# 01 — Architecture

What this package IS: one runner model behind six constructors, one chain that needs none, source trees with declared edges, and seven channels through which its conventions are enforced — each row of the catalogue naming exactly one. The chapters that follow explain how to USE each facet; this one draws the lines they sit inside.

## The runner model

Every facet is the same four steps. A **constructor** takes options and returns a **handle**; the handle opens a **chain** of zero or more setups closed by exactly one terminal action; the action executes and resolves to a **typed result**; the result is asserted through vitest's `expect()`. Nothing else is public — there is no imperative escape hatch, because a spec that can do anything proves nothing in particular.

Six constructors exist and the list is closed (`src/facets/specification.ts`):

| Constructor                   | Handle destructures to      | Subject under test                               |
| ----------------------------- | --------------------------- | ------------------------------------------------ |
| `specification.api()`         | `{ api, cleanup, docker }`  | An HTTP API, built and served in this process    |
| `specification.job()`         | `{ job, cleanup }`          | A background pipeline, triggered by name         |
| `specification.cli()`         | `{ cli, cleanup, docker }`  | A command binary in a fresh temp directory       |
| `specification.integration()` | `{ integration, cleanup }`  | A module against real services, or a golden      |
| `specification.website()`     | `{ website, cleanup, url }` | A rendered page — fetched, or driven in chromium |
| `specification.mobile()`      | `{ mobile, cleanup, udid }` | A native screen on an iOS simulator              |

The asymmetry in that column is the model, not an oversight: `docker` reads a container the subject itself started, and neither a pipeline triggered by name nor a module called in-process is specified by the containers it starts, so `job` and `integration` are handed none; `website` and `mobile` drive a browser and a simulator rather than an orchestrated stack, so they carry neither.

**One facet has no constructor**, and the same reason explains it: a rendered component starts nothing. `component` ([07 — Component specs](07-component.md)) is a chain the package exports directly — `component.intercept(…).render(<X />)` — so there is no handle to destructure and no `cleanup` to pass to `afterAll`. What every render of a project shares (the providers, the Vite pipeline, the viewport) is the PROJECT's, stated once by `component()` in `vitest.config.ts`.

A runner is created **once per suite**, in a `*.specification.ts` file, and imported by the test files beside it. That split is what makes the container lifecycle affordable — one Postgres per suite, not one per test — and it is why `afterAll(cleanup)` belongs in the specification file and nowhere else.

### The seam under the chain

A facet's chain is COMPOSED: `src/facets/<facet>/<facet>.facet.ts` lists the setups (each a `*.capability.ts`) and the terminal actions (each a `*.action.ts`) it is made of and the engine each one is armed through, `defineFacet` opens the chain, and every action runs through the one pipeline of `src/kernel/chain/perform.ts`. Every facet — `job`, `api`, `website`, `integration`, `cli`, `mobile` and `component` — is composed, and there is no other chain. The infrastructure a chain needs is reached through **ports** — each a `*.port.ts` beside the area or the facet that owns it (`database`, `service`, `container`, `isolation` under `src/world/services/`; `server`, `cli`, `browser`, `device` in their facet) — and an adapter implements one. So the chain knows "a database exists"; it never knows Postgres.

Every seam is opened lazily rather than imported, and each one is an optional peer loaded by the one module that owns it, so a project that tests no page, no component and no database installs none of them. Which peer each facet and each service needs, and what its refusal says, is [04 — Operating § What a consumer must bring](04-operating.md#what-a-consumer-must-bring)'s list; a service's refusal is built by `src/world/services/peer.ts`, and a facet's by the adapter that loads its peer.

## The source trees

The code is trees with declared, one-directional edges: the product under `src/`, and `lint/` at the repository root beside it — the rules the package ships (the spine: `src/`, `lint/`, `specs/`, `docs/`, `skills/`). The map is not the linter's to assume — `import-within-declared-layers` ships inert — so this package declares its own as `FRAMEWORK_LAYERS` in `lint/self/checks/layers.ts`, which `oxlint.config.ts` wires, and that declaration is the enforced statement of what follows.

The folders import one way — `reading/` and `catalogue/` under the rules, the checks and the ratchet, those under the entry; only `self/` imports `self/`, and only the checker's command line imports `migration/`. The enforced statement is a self checker pass's, listed in [03 — Testing § The package's own rules](03-testing.md#the-packages-own-rules).

**A setup is defined once, whatever the facet.** A second copy of "declare a stub, seed a table, run the thing" is how two facets drift, so a facet never implements one: it composes the definition and names the engine it is armed through, and its chain type is computed from the same list (`src/kernel/chain/chain.ts`), each chain published as an interface so a compiler message prints its name. Every facet's `<facet>.facet.ts` names that chain beside its composition, so the facet's own folder says what its constructor hands out; `component`, which has no constructor, is opened once by its own page face, `facets/component/index.browser.ts`, which the page's entry re-exports.

The edges point one way: `kernel ← world · elements · expectations ← facets ← vitest · the entries`. Some carry their reason in the declaration itself. `world/stubs/` reaches `expectations/tokens/` because a stub's request filter IS an expectation on the outgoing request — one `match.*` and `{{token}}` grammar, never a second. A facet's `<facet>.project.ts` reaches `vitest/project-kit` because the kit runs only in the Vitest main process, never in test code, and `vitest/` reaches the one vite plugin a facet owns, the cli's literate door, through that facet's project. `lint/` reaches exactly the modules the runner also uses — the token list, the ground names, the stub kinds, the root walk and the tree it walks (`kernel/files/git-tree`: what git does not ignore), the `<case>.spec.yaml` parser — so that the file the lint accepts is the file the runner runs, from ONE parser. What the map cannot express is held by the self checker passes under `lint/self/checks/`, one file per pass over the walk `source.ts` shares, each finding at the entry, the import or the folder it names: the source root holds the entries, their tests and the six trees alone, a facet never imports another, a concept folder is reached only from inside its facet, and each third-party engine is imported by exactly one slice (`playwright` by `facets/website/`, `webdriverio` by `facets/mobile/`, `msw` by `world/stubs/network/`, `pg` by `world/services/postgres/` …); a node builtin is no engine, and each slice spawns only the program its own concept owns ([ADR-009](decisions/009-node-builtins-are-not-engines.md)). Swapping the runner would be a rewrite of `vitest/`, the facets' projects, the component's page and the few bricks built on a vitest primitive — the clock (`vi`), the scratch directory (`onTestFinished`), the doubles (`vitest-mock-extended`) and the goldens, whose matchers are registered on vitest's `expect` — and of nothing else.

This package's product IS test tooling, so `no-test-code-in-production` — which keeps a consumer's production away from test material — is turned off by path wherever that is the job: `vitest/`, each facet's project, the run's global setups, the component's page, the website's playwright adapter, the msw network engines, the clock, the doubles, the scratch directory, the goldens and update mode. Every other module is held to it — the entries and the facet constructors included, which is why a constructor is named `<facet>.handle.ts` and never by a suffix `no-test-code-in-production` reads as test material; and no module a bundle is built from may be test material, which `package-exports.test.ts` reads from the build's source maps.

The table's May-import column is a reading of `FRAMEWORK_LAYERS`, never a second statement of it: the declaration in `lint/self/checks/layers.ts` is what the linter enforces and what a change edits.

There are TWO composition roots and neither names a layer. `src/index.ts` is node's: re-exports only — each facet's face (`src/facets/<facet>/index.ts`, the names that facet contributes) and the modules of the other layers by path. `src/index.browser.ts` is the page's: it publishes the node entry's types whole and every value a page can run, refusing the node-only ones — see [What the tree publishes](#what-the-tree-publishes).

## The seven enforcement channels

A convention this package states is held by a **channel**, and every row of the catalogue names exactly one of seven. The guiding aim is that most enforcement is programmatic, not review-borne.

- **statique** — the `jterrazz/*` oxlint plugin: one file per rule under `lint/rules/<family>/`, the folder of its catalogue family — AST analysis, one diagnostic per file.
- **upstream** — a convention an oxlint vitest-plugin rule already holds, set as an OPTION from the `testing` fragment rather than duplicated as a rule of ours ([ADR-005](decisions/005-the-doubles-ladder-is-closed.md)).
- **checker** — passes of the `jterrazz-test-check` binary reading what an AST cannot: the `{{token}}` grammar of `requests/` and `expected/` fixtures, the `<case>.spec.yaml` document family, cross-file analyses that cross a `*.specification.ts` with its tests, and the member pass that judges a package rather than a tree.
- **runtime** — the framework refuses incorrect usage as it executes, where static analysis abstains (a non-literal argument) or cannot reach (the network, a container lifecycle).
- **type** — what the compiler refuses with no rule at all, proven by `src/type-channel.test-d.ts`.
- **meta** — what the framework's own suite holds about itself: the catalogue's freshness, its completeness, the reach of its rules — [03 — Testing](03-testing.md) owns the channel.
- **process** — the judgement no single channel settles: asset-driven grouping, golden-file discipline, retro-propagation.

The channel a rule sits on is not prose here: it is a field of `lint/catalogue/manifest.ts`, the single source of truth from which the catalogue in [19 — Linting](19-linting.md) is generated. So is its audience: a `consumer` rule is what a project using the package meets and is listed there, a `self` rule holds only this package's own suite, has its row in `lint/self/catalogue/manifest.ts`, and is listed in [03 — Testing § The package's own rules](03-testing.md#the-packages-own-rules). A rule and its normative sentence live together in the code, so the two cannot drift.

## What the tree publishes

The bundle is built by `tsdown` into `dist/` and its shape follows how each entry is consumed. `index` and `vitest`, plus the `checker`/`catalogue` CLIs, are ESM-only — vitest is ESM-only and the CLIs are invoked as `node dist/*.js`. The `oxlint` plugin ships dual, because oxlint loads it from a consumer project that may itself be CommonJS.

**There are FOUR entries and no more**: `@jterrazz/test` for everything a spec uses, `@jterrazz/test/vitest` for what `vitest.config.ts` needs, `@jterrazz/test/oxlint` for the lint plugin, `@jterrazz/test/schema` for an editor validating a `<case>.spec.yaml`. That is rule `no-unpublished-subpath` rather than a convention of taste, and the exemption is derived from the manifest's own `exports` map (`lint/reading/package-exports.ts`), so a subpath is exempt the moment it is published and stops being exempt the moment it is withdrawn.

**The root entry has two runtimes.** A component test renders in a real browser, and the node entry cannot load there: it wires `pg`, `better-sqlite3`, `testcontainers` and `node:fs` at import. So `exports["."]` carries a `browser` condition resolving to `dist/browser/index.js` — the same public surface, built for a page, where every node-only name (the six constructors, the services, the docker accessors, the results that walk a disk) is a stub that throws where it was called, naming the facet and saying it runs under node. The split is the RUNTIME's and never the facets': one specifier, so no spec has to remember which entry it may import.

`types` is stated once, and it is the node build's — so the two runtimes are ONE type surface and a name cannot exist on one side only. The page's entry takes its types from the node's (`export type *`), so they cannot drift, and the `package-exports` meta-test compares the two builds' exported names on every run.

The API is the types the package publishes, and nothing re-states it. What the code does project into the corpus is a set of generated tables and `schema/spec.schema.json`, generated from the document grammar's own constants; which tables, and the one gesture that writes them, is [02 — Developing § What a change owes](02-developing.md#what-a-change-owes)'s list. Both `docs/` and `schema/` ship in the tarball, `docs/` less the two pages that are this repository's own, so a consumer reads the manual where the messages send them, inside the install ([04 — Operating](04-operating.md#what-leaves-the-tree) names the two). All of them are held fresh by meta-tests.

## Pitfalls

- **Reaching for a dependency from `kernel/`.** A new external package belongs to the ONE slice that needs it — a world area or a facet — and nowhere else. Only an engine every layer truly shares sits behind the kernel, each in the one folder `FRAMEWORK_LAYERS` grants it to: `yaml` in `yaml/`, vitest's test hooks in `files/`, the toolchain's config types in `config/`. Anything else the kernel imports is the boundary this package cannot afford to blur, and `import-within-declared-layers` and the engine-ownership rule refuse it.
- **Adding a seventh constructor.** The six are the closed vocabulary the conventions, the linter and the documentation are all shaped around. A new SUBJECT to specify is a design decision, and it earns a record in [`decisions/`](decisions/) before it earns a constructor — as `integration` did in [ADR-004](decisions/004-a-module-against-real-services-or-a-golden-is-the-integration-facet.md).
- **Writing a rule's normative sentence into a chapter.** It belongs in `lint/catalogue/manifest.ts` beside the implementation; a chapter that restates it is the second copy the whole design exists to prevent.
